# 19 日志、事件与记忆可视化

## 1. 文档目标

本文件定义 Ayes 当前阶段的可观测性和可视化查看要求。

重点不是“把日志写出来”，而是让用户和后续 Agent 都能明确知道：

- 刚才发生了什么
- 为什么发生
- 为什么没有发生

## 2. 必须可查看的对象

当前阶段至少必须可查看以下四类内容：

- 运行日志
- 近期事件
- 短期记忆
- 最近告警 / 命中记录

## 3. 日志分类

日志至少分为：

- `system`
- `watch`
- `capture`
- `diff`
- `ocr`
- `match`
- `alert`
- `action`
- `api`

## 4. 日志展示要求

前端中应支持：

- 查看最近日志
- 按类别过滤
- 按任务过滤
- 查看时间
- 查看摘要

当前阶段可以先不做复杂全文检索，但必须能让用户直观看到最近运行状态。

## 5. 近期事件展示要求

事件展示至少包括：

- 事件时间
- 事件类型
- 事件摘要
- 目标类型 / 目标标识
- OCR 文本摘要
- OCR 质量摘要，例如 provider、字符数、块数、平均置信度、是否稀疏
- 区域名称 / ROI 标识
- 必要坐标信息
- 视觉摘要
- 是否命中监控条件

## 6. 短期记忆展示要求

短期记忆展示至少包括：

- 时间范围
- 最近 N 分钟
- 结构化回答摘要
- 关联事件列表
- 证据引用
- 最近记忆条目列表
- 条目级时间、摘要、位置摘要与可选证据预览

## 7. 排查导向要求

可视化能力必须支持排查以下问题：

- 为什么没有识别到文字
- 为什么该区域被当成图表或图片区
- 为什么这次触发了视觉增强，或者为什么被跳过
- 为什么没有命中条件
- 为什么没有发 webhook
- 为什么当前窗口没有进入主监控链路
- 为什么最近问答没有结果

## 8. 与 API 的关系

日志、事件、记忆和最近命中记录都不应只存在前端局部状态。

必须保留统一查询接口，以便后续：

- Web 工作台读取
- CLI 调试
- Agent / skill 调用

## 9. 当前阶段结论

后续开发必须把“日志、事件、记忆可视化”视为正式交付内容，而不是调试附属品。

如果监控正在运行，但用户看不到近期事件、看不到短期记忆、看不到日志，就不能算真正可用。

## 10. 当前实现校准

当前代码已落地以下可视化读取路径：

- `/api/events`
- `/api/memory/recent`
- `/api/ask`
- `/api/logs`
- `/api/status`
- `/api/screenshot`
- `/api/timeline/recent`
- `/api/timeline/long-term`
- `/api/watch/status`

当前前端已可以直接显示：

- 近期事件
- OCR 片段辅助视图
- 长期摘要
- 短期记忆 / 问答结果
- 近期日志
- 当前截图预览
- 当前监控状态
- 事件与问答中的截图证据链接

持续监控补齐后，工作台还应明确显示：

- 当前是否已装载任务
- 当前是否后台持续运行中
- 持续监控启动/停止后的最近日志
- 最近一次执行时间
- 最近一次事件时间
- 最近一次后台错误状态

当前阶段建议进一步按来源拆分查看：

- 普通事件时间线
- 动作时间线
- 命中时间线
- 告警时间线

后续还需要继续增强：

- 日志分类过滤
- 长期记忆可视化
- 告警记录可视化与真实发送审计
- 结构化问答结果的更好展示
- 时间范围切换与任务切换

当前实现补充：

- 已新增 `/api/ocr/snippets`，按任务和最近时间范围返回 OCR 文本片段
- 当前工作台可直接查看最近识别出的文本，辅助配置 triggered 关键词和排查未命中原因
- 告警链路已开始写入 `alert_sent`、`alert_failed`、`alert_suppressed` 事件，供“告警轨迹”查看
- 已新增可复用的本地 HTTP smoke 脚本，用于验证 `status / timeline / snippets / logs / ask` 闭环链路
- OCR 事件当前已开始附带轻量质量摘要，包含 provider、字符数、块数、平均置信度和稀疏标记，便于人工判断“这次 OCR 是否可靠”
- 当视觉增强开关启用时，当前已开始写入 `vision_triggered` / `vision_skipped` 审计事件，并附带触发原因、阻断原因、模型名与 provider，便于排查“为什么这次该交给视觉模型”

其中“更好展示”的当前阶段最低要求为：

- 问答回答与命中事件分开展示
- 明确显示 `minutes` 时间范围
- 明确显示 `memory_layers_used`
- 事件和日志至少支持最近时间和类别两个基础维度的人工排查
- 近期事件、OCR 片段、动作轨迹、命中轨迹、告警轨迹、长期摘要、日志等面板，应显式显示各自的查询上下文，包括 `task_id / minutes / source|category / count`
- 当当前过滤范围下没有结果时，界面应直接说明“当前范围内没有相关结果”，避免用户误判为服务未运行或界面未刷新

补充要求：

- 如果事件或问答结果已具备截图证据引用，则前端应优先支持直接预览缩略图，而不是只显示纯文本路径
- 用户应能在近期事件区或问答证据区直接判断“这张图是不是我要看的那一次画面”
- 直接预览可以先基于本地静态文件路径实现，不要求第一阶段就引入复杂媒体管理服务
- 近期事件时间线、动作时间线、命中时间线、告警时间线都应尽量复用同一套证据预览能力，避免只有问答区能看图、时间线却还停留在纯文本路径

证据清理补充要求：

- 截图证据不是无限保留的，必须随短期详细记忆窗口做基础清理
- 当前 MVP 至少应支持按短期记忆保留时长删除过期证据，并在日志中留下清理记录
- 在尚未建立长期证据引用计数前，第一阶段可以采用“短期窗口 + 缓冲时间 + 保留少量最新文件”的保守清理策略
- 后续若长期轻量记忆明确引用证据文件，则应进一步升级为基于引用关系的清理，而不是单纯按文件年龄删除
