# 03 监控对象与采集约束

## 1. 第一优先监控对象

当前唯一最高优先监控对象是：

> 指定进程下的所有窗口。

包括但不限于：

- 主窗口
- 子窗口
- 弹窗
- 新开窗口
- 后台窗口
- 被遮挡窗口
- 折叠窗口
- 最小化窗口

同时第一阶段也应支持：

- 整个屏幕监控

## 2. 采集目标

目标不是只监控当前前台可见窗口，而是尽可能覆盖指定进程全窗口的可观测变化。

用户在选择监控目标时，不应只看到抽象进程名或窗口 id，而应尽量看到：

- 进程名
- 窗口预览画面
- 屏幕预览画面
- 基本标题或描述信息

交互目标应接近共享屏幕软件中的选择方式：用户通过可视化罗列结果点击选择。

## 3. 必须拆开的两个概念

第一阶段必须明确区分：

- 窗口状态可观测
- 窗口像素可采集

这两个概念不能混用。

## 4. 采集层职责

采集层负责：

- 枚举进程关联窗口
- 跟踪窗口新增、关闭、隐藏、最小化和层级变化
- 尝试对目标窗口进行周期性采样
- 记录采样成功、失败和不可见状态
- 对无法直接采集像素的窗口保留状态事件

第一阶段窗口发现与采集实现需要预留跨平台抽象，但当前首个验证环境仍然是 macOS。

因此应采用两层设计：

- 平台无关的 `WindowDiscovery` / `WindowCapture` 抽象接口
- 平台相关的 `macOS` 首个实现

## 5. 当前 macOS 窗口发现验证结论

基于 `PyObjC + Quartz` 的初步验证已确认：

- 可以枚举系统窗口列表
- 可以拿到 `owner PID`
- 可以拿到 `owner name`
- 可以拿到 `window number`
- 可以拿到 `layer`
- 可以拿到 `bounds`
- 可以拿到部分 `onscreen` 状态

但当前验证也显示：

- `window title` 经常为空
- 同一进程下会混入多个辅助窗口、装饰窗口和非业务窗口
- `onscreen` 字段并不总是稳定返回布尔值
- 仅凭系统窗口列表不能直接得到“业务上有意义的窗口集合”

因此第一阶段必须增加：

- 窗口过滤层
- 主窗口/业务窗口判定层
- 窗口可观测性标记
- 业务窗口候选排序逻辑

## 6. 业务窗口筛选原则

用户虽然选择的是“指定进程下的所有窗口”，但 Ayes 不应把所有系统返回窗口都纳入实际监控集合。

第一阶段必须筛掉以下窗口：

- 没有可观测画面的窗口
- 仅用于装饰的窗口
- 极小尺寸的辅助窗口
- 明显不是业务内容承载面的系统附属窗口

因此第一阶段的实际策略应是：

1. 先枚举指定进程全部窗口
2. 再判断哪些窗口具备可观测画面
3. 只将“有画面且有业务价值”的窗口纳入监控候选集
4. 对无画面窗口仅保留元数据，不进入 OCR / 变化检测主链路

补充约束：

- `process` 目标在 v1 运行时每个采样 tick 只选择一个当前最优代表业务窗口进入主采样链路
- 该代表窗口应优先满足“业务窗口、可观测、标题更明确、面积更大”等条件
- 如果指定进程当前没有满足约束的可采集业务窗口，必须输出显式状态事件，而不是静默退回整屏截图冒充进程监控

## 7. 监控目标选择方式

第一阶段建议提供两类选择入口：

1. 选择整个屏幕
2. 选择指定进程下的业务窗口

其中窗口选择界面应尽量提供：

- 缩略图预览
- 进程名
- 窗口标题或可读标签
- 是否当前可观测

目标不是让用户理解底层窗口结构，而是让用户像使用共享屏幕软件一样直接点选监控对象。

## 8. 最小化和折叠窗口约束

“最小化窗口也要尽量检测到”是核心产品要求，但第一阶段必须承认现实限制：

- 某些窗口状态下可以拿到元数据，但拿不到实时像素
- 某些状态下只能间接采样
- 某些应用后台渲染策略可能导致窗口不可直接观测

因此第一阶段原则如下：

1. 先保证窗口状态感知
2. 能采像素时再进入变化识别
3. 不能采像素时至少写入状态变化事件
4. 恢复可采集后尽快补齐变化分析

对 `window` / `process` 目标还必须补充：

- 当原窗口 id 消失、进程代表窗口不可得、或当前状态无法稳定抓图时，应直接输出 `capture_status`
- 不允许自动切到整屏继续 OCR，并让用户误以为仍在看原目标

最小化窗口下的受控点击也必须遵守同样的现实约束：

- 如果目标窗口在当前平台或当前状态下不可稳定定位、不可稳定激活、不可稳定接收点击，则不能承诺“最小化状态下仍可可靠点击刷新”
- 第一阶段应优先支持前台、可观测、可绑定坐标的窗口点击
- 对最小化窗口，必须先验证该平台是否能稳定恢复点击路径，否则只能记录为不支持或需要先恢复窗口

## 9. 第一阶段采集结论

第一阶段产品承诺不是“任何最小化窗口都能稳定拿到实时像素”，而是：

- 尽量提升全窗口可观测性
- 明确记录窗口状态
- 把可观测性纳入事件模型
- 避免对不可采集状态做虚假承诺

当前 macOS 初步验证还表明：

- 整屏截图可行
- 部分窗口级截图可行
- 部分窗口即使存在元数据，也无法直接获取图像

因此第一阶段必须把“窗口是否有可抓取画面”作为单独判定条件。

同理，第一阶段也必须把“窗口是否有可执行点击路径”作为单独判定条件，而不是假设只要枚举到了窗口就一定能点。

## 10. 最新窗口采集矩阵验证结论

当前仓库已补充真实验证脚本：

- [scripts/verify_window_capture_matrix.py](/Users/apple/Desktop/2026/Ayes/scripts/verify_window_capture_matrix.py)

脚本会：

- 先枚举 macOS 当前窗口候选
- 再对前 50 个窗口逐个尝试窗口级截图
- 输出实际抓图结果矩阵到：
  - [runtime/window_capture_matrix.json](/Users/apple/Desktop/2026/Ayes/runtime/window_capture_matrix.json)

当前一次真实抽样结果表明：

- 总窗口数：`237`
- 抽样测试窗口数：`50`
- `expected_capture_result = recommended` 的窗口中，当前抽样大多可以实际抓图成功
- `expected_capture_result = best_effort` 的窗口中，当前抽样大量返回 `no_pixels`

当前这次抽样统计为：

- `actual_ok = 28`
- `actual_failed = 22`

且失败样本几乎全部集中在：

- `is_onscreen = false`
- `observable_state = 部分可观测`

这说明第一阶段在 macOS 上必须明确采用以下判断：

1. `onscreen + 有像素` 的窗口，进入主采样链路优先级最高
2. `有元数据但不在 onscreen` 的窗口，只能视为 `best_effort`
3. 对 `best_effort` 窗口不能承诺持续稳定拿到实时像素
4. 对抓图失败窗口，应继续保留元数据和状态事件，但不强行进入 OCR 主链路
