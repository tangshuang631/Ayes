# Ayes 项目规则

## 1. 规则地位

`docs` 目录下的项目规则和开发文档是本项目当前唯一最高参考。

任何实现、重构、调研、临时方案和后续开发，都必须先对齐 `docs`，再进入代码或脚本改动。

## 2. 文档结构规则

`docs` 目录只允许存在以下两类正式文档：

- 项目规则文档
- 开发文档体系

开发文档体系必须由以下两部分组成：

- 一份主开发文档索引
- 多份按功能、结构、模块拆分的开发文档

## 3. 主开发文档规则

主开发文档必须放在 `docs` 根目录下，并承担索引职责。

主开发文档负责：

- 说明项目定位
- 说明文档使用方式
- 维护编号索引
- 指向各模块开发文档
- 说明哪些文档是当前有效开发依据

主开发文档不应再承载所有详细内容，详细内容必须下沉到按模块拆分的文档中。

## 4. 模块文档规则

模块开发文档必须：

- 放在 `docs` 根目录下
- 采用统一编号
- 按功能或结构边界拆分
- 标题和文件名可直接反映模块主题

模块文档的修改原则：

1. 先改开发文档
2. 再按开发文档推进实现
3. 不允许绕过开发文档直接做与文档冲突的实现

## 4.1 编码规则

本项目源码、配置、文档、脚本默认统一使用 `UTF-8` 编码。

要求：

- 必须避免混用其他编码
- 必须避免中文内容在源码、配置、日志和文档中出现乱码
- 与外部输入输出交互时，应显式按 `UTF-8` 处理
- 如果某个依赖或外部数据源使用非 `UTF-8`，需要在接入点做明确转换

## 4.2 开发完成标准规则

对 Ayes 这类面向人类用户和 Agent 的工具项目，默认禁止只完成“后端链路存在但几乎不可见、不可直接操作、不可直接核验”的半成品。

后续每个关键阶段至少应同时满足以下要求：

- 有可直接操作的入口
- 有可直接查看的结果
- 有可直接核验的运行状态

具体要求：

- 不能只停留在脚本、测试或 JSON 输出层面
- 必须尽快提供可用的本地 Web 前端工作台或等价的人类可视化界面
- 前端中必须可查看当前监控任务、近期事件、短期记忆、关键日志和运行状态
- 如果一个能力已经完成实现，但用户在界面中无法理解、无法验证、无法观察其效果，则默认不算真正可用

## 4.3 前端规则

Ayes 的前端默认采用：

- 简洁
- 高信息密度
- 无卡片化堆叠
- 以分栏、列表、表格、时间线、分割线为主

明确要求：

- 尽量不用大面积卡片堆叠来组织主要信息
- 不允许把近期事件、记忆、日志、监控状态全部切成一堆割裂卡片
- 优先使用一体化工作台布局
- 重要状态、当前目标、最新事件、问答输入、日志入口应在同一工作台中快速可达
- 风格应接近成熟工具产品，而不是宣传页或模板化 dashboard

## 4.3.1 当前工作台视觉风格参考

当前阶段 Web 工作台的视觉风格参考文档为：

- [00-前端设计参考DESIGN.md](/Users/apple/Desktop/2026/Ayes/docs/00-前端设计参考DESIGN.md)

正式约束：

- 保留当前工作台已有的信息结构、功能模块和组件能力
- 优先调整视觉风格、间距、字体层级、圆角、颜色和交互细节
- 不允许为了套用风格参考而打散现有监控工作台的信息架构
- 仍应坚持“一体化工作台”而不是营销页、着陆页或大卡片堆叠

当前风格落地方向：

- 参考 Ollama 风格的克制、留白、黑白灰中性配色和 pill 几何
- 保留 Ayes 作为监控工作台所需的高信息密度和快速扫描能力
- 允许使用少量浅色 surface 区分输入区、预览区和只读结果区，但不得回到厚重卡片化界面

## 4.4 日志与可观测性规则

日志不是附属项，而是 Ayes 第一阶段和后续阶段的正式能力之一。

要求：

- 必须有结构化运行日志
- 必须区分系统日志、监控任务日志、动作日志、告警日志
- 必须支持在本地界面中直接查看近期日志
- 必须支持在本地界面中直接查看短期记忆和近期事件
- 日志和事件不能只落盘不展示
- 用户必须能够用界面理解“刚才发生了什么”“为什么没有触发”“为什么没有告警”

补充要求：

- 本地 Web 工作台中必须存在“近期事件”“短期记忆”“长期摘要”“近期日志”的直接查看入口
- 用户不得依赖命令行或数据库工具才能理解当前监控状态
- 日志、事件、记忆三者应支持同一任务上下文下的联合排查
- 至少应支持按任务、最近时间范围、日志类别三个维度进行人工查看
- 工作台主视图必须提供一层首屏可核验信息，但默认应以“当前原始读取结果”优先，而不是固定统计盘
- 首屏状态区必须至少能直接看到当前目标、最近采集状态、最近 OCR 摘要、最近视觉判断和最近视觉补充结果
- 如果目标类型为 `process` 或 `window`，首屏还必须直接显示最近实际捕获到的 `process / window_title / window_id / window_state`，避免用户只看到进程名却不知道当前实际盯的是哪个窗口
- 首屏运行元信息还必须直接暴露“后台持续监控是否正在运行”“当前前端连接数”“最近一次实际捕获目标摘要”，不应要求用户去读原始 JSON 才能确认服务状态
- 首屏状态区默认不展示独立统计盘、计数卡或面向长期观察的 dashboard 数字；命中数、告警数、日志数、记忆条目数等聚合信息应下沉到对应面板
- 对于变化频繁且任务定义经常变化的监控场景，首屏应优先回答“刚刚从这个目标读到了什么”，而不是展示一组容易失真的固定统计摘要
- 用户打开页面后，应能在不翻阅多个面板的情况下，快速判断以下问题：
  - 当前监控是否真的在持续看屏幕
  - 最近 OCR 是否过于稀疏或不可靠
  - 最近是否触发过视觉补强，以及为什么触发或未触发
  - 最近是否命中过条件、发出过告警、出现过错误或异常日志
  - 最近是否已经积累了足够的短期记忆与可回放证据
- 高频核验信息允许分布在事件、日志、记忆、命中、告警面板中，但首屏必须先回答“刚刚读到了什么”

## 4.5 Agent 接入规则

Ayes 后续必须面向 Agent / skill / tool 接入。

因此后续开发必须遵守：

- 前端只是工作台，不得把核心能力写死在前端内部
- 所有关键能力都必须保留 API / service 化边界
- 监控任务、记忆查询、事件查询、日志查询、告警状态查询都应具备后续被 Agent 调用的清晰接口
- 新增 UI 能力时，必须同步考虑其对应的服务接口，而不是只做页面内部状态

## 4.5.2 当前主入口规则

从当前阶段开始，Ayes 的默认主入口不再是“人类长时间停留在复杂 Web 工作台中操作全部能力”，而是以下双入口：

- `Codex skill / 本地工具 + Ayes 本地 HTTP API`
- `轻量 Web 工作台`

其中：

- `Codex skill / 本地工具 + Ayes 本地 HTTP API` 是后续 Agent 使用的第一主入口
- `轻量 Web 工作台` 只负责：
  - 目标发现
  - ROI 框选
  - watch spec 配置
  - 启停监控
  - 人类核验当前截图、事件、记忆、日志与问答结果

明确约束：

- 不允许继续把低频调试面板堆在首屏
- 不允许让用户进入页面后仍看不出“先选目标、再装载任务、再启动监控、再看证据、再提问”的主路径
- 对 Agent 更有价值的能力，应优先沉淀为稳定 API、CLI 命令或 skill 工具，而不是优先做新的页面交互
- Web 工作台必须服务于“配置与核验”，而不是变成主业务承载层
- 若前端与 skill 路线冲突，应优先保证 skill / API / CLI 的稳定合同

## 4.5.3 Skill 产物规则

后续凡是面向 Codex / Agent 的 Ayes skill，必须在仓库中保留以下正式产物：

- `skills/<skill-name>/SKILL.md`
- `skills/<skill-name>/agents/openai.yaml`
- `skills/<skill-name>/references/`
- 如有必要，补充极薄的本地工具命令或脚本，避免 skill 直接内嵌复杂 HTTP 细节
- 如需正式安装到 Agent skill 根目录，必须提供仓库内安装脚本

要求：

- skill 文案必须清楚说明何时使用 Ayes
- `SKILL.md` 保持简洁，安装说明、命令清单、排障说明应拆到 `references/`
- skill 必须优先调用本地稳定接口，而不是依赖前端页面状态
- skill 需要覆盖：
  - 目标装载或任务发现
  - 监控启动 / 停止 / 状态读取
  - 最近事件 / 记忆 / 问答读取
  - 截图证据或关键证据读取
- 正式安装脚本必须能够生成绑定当前仓库路径的本地包装命令，避免 Agent 会话手写 `PYTHONPATH` 或手写 curl

如果接口调整导致 skill 使用路径变化，必须先更新正式文档和 skill 文档，再更新实现。

## 4.8 提交规则

本项目提交信息默认必须使用详细中文，且应准确说明：

- 改了哪些模块
- 为什么改
- 当前验证做了什么

不允许使用过短、不可追溯或信息量过低的提交信息。

## 4.5.1 视觉增强策略规则

Ayes 的第一阶段主链路固定为：

- OCR
- 变化检测
- 轻量视觉标签
- 语义匹配

如果后续接入本地小型视觉模型，其定位必须是：

- OCR 主链路的增强层
- 图片、图标、图表、弹窗样式、颜色状态等非文本信息的补充层
- 仅在高价值场景按需触发的能力层

明确约束：

- 不允许把“每帧都跑视觉模型”作为第一阶段默认实现
- 不允许让视觉模型替代事件模型、记忆模型和问答检索链路
- 不允许把平台专属视觉能力写死到上层业务逻辑
- 视觉增强的输入输出也必须保留统一抽象边界，便于后续 skill / agent 接入

推荐触发条件：

- OCR 置信度不足
- 差分明显但文本变化很少
- 用户明确要求监控图表、图片、图标、颜色或非文本状态
- 需要补充 OCR 无法覆盖的视觉证据

## 4.6 目标驱动开发规则

当项目已设定明确开发目标后，后续开发默认按目标持续推进，不得随意中断在“有部分代码、有部分接口、但仍不足以人工验证核心链路”的状态。

要求：

- 目标必须尽量具体，且包含可核验结果
- 如果线程中已存在与当前需求一致的活跃目标，应继续沿用，不重复制造模糊目标
- 每推进一轮实现，都应同步核对当前目标是否仍然成立
- 若新增需求改变阶段边界，必须先回写正式开发文档，再调整实现和验收标准
- 未达到当前阶段最小可人工核验标准前，不应宣称阶段完成

当前阶段默认最小可人工核验标准包括：

- 可从本地 Web 工作台完成目标选择或任务切换
- 可直接查看近期事件、短期记忆、长期摘要和近期日志
- 可按任务和最近时间范围发起问答
- 可通过界面理解最近发生了什么、命中了什么、为什么没有命中

如果阶段目标是“可人工核验的核心链路 MVP”，则默认还必须满足：

- 前端工作台已接入真实 API，而不是纯静态示意
- 工作台可直接显示当前任务、运行状态、近期截图或等价视觉证据
- 工作台可直接查看近期动作、命中、告警或未告警原因
- 至少有一条从“选目标 -> 启动/执行监控 -> 查看事件/记忆/日志 -> 发起提问”的闭环链路
- 不允许用整屏回退伪装“进程监控”或“窗口监控”已经可用；如果目标解析失败，必须显式产出状态事件与日志，向用户说明当前没有真正看见目标画面

## 4.7 后台服务生命周期规则

Ayes 当前阶段必须采用“后台服务与前端工作台解耦”的运行方式。

要求：

- 监控已启动时，关闭前端页面、浏览器或 Web 工作台标签页，不得导致监控中断
- 前端页面只是连接后台服务的入口，不得成为监控运行的前提
- 当且仅当“当前没有持续监控运行”且“没有前端连接存在”时，后台服务才允许自动退出
- 自动退出逻辑必须由稳定的外部生命周期管理层或等价机制控制，不得用脆弱的页面状态直接决定监控进程生死
- 桌面启动器必须按单实例后台设计，不得重复启动多个 Ayes 服务实例

## 5. 编号与索引规则

`docs` 下的正式文档必须编号。

建议约定：

- `00-`：项目规则
- `01-`：主开发文档索引
- `02-` 及以后：按模块拆分的开发文档

每次新增正式文档时，必须：

- 更新主开发文档索引
- 保证编号有序
- 保证标题清晰

## 6. 修改流程规则

当需求、定位、MVP、模块边界、接口、数据结构发生变化时，必须按以下顺序处理：

1. 先修改对应开发文档
2. 确认主开发文档索引是否需要同步
3. 再开始实现代码或脚本改动
4. 实现完成后，如实际方案与文档存在偏差，必须回写文档

## 6.1 提交规则

git 提交信息必须使用详细中文。

要求：

- 必须能直接说明本次提交解决了什么问题或补充了什么文档
- 不能只写模糊词，例如 `update`、`fix`、`misc`
- 优先写成“动作 + 对象 + 目的”的形式

示例：

- `文档：补充企业微信 webhook 告警策略与失败审计规则`
- `文档：定义问答混合检索路径与长期记忆时间范围约束`
- `实现：增加窗口发现过滤层并记录可观测状态`

如果一次提交同时包含“文档回写 + 实现落地 + 测试补充”，提交信息应明确体现三者关系，避免只写成模糊的“大更新”。

里程碑提交约束：

- 完成一个可核验里程碑后，必须先完成必要验证，再推送到远端开发分支
- 推送前必须明确本次里程碑的验证范围，不得把“仅写完代码但未验证”的状态当作可交付里程碑
- 推送后如仍有未完成项，应继续以正式开发文档为准推进，不得把已推送误当作阶段完成

## 7. 临时文档规则

临时开发文档必须全部放在 `docs/temp` 目录下。

临时文档命名必须采用：

`YYYY-MM-DD-目的.md`

例如：

- `2026-06-23-采集链路调研.md`
- `2026-06-23-OCR选型对比.md`

临时文档规则：

- 只能服务于短期调研、验证、草案或阶段性记录
- 不能与正式开发文档命名冲突
- 不能替代正式开发文档
- 内容一旦被正式吸收，必须及时删除或清理
- 必须采用清单形式编写，使用 `- [ ]` 和 `- [x]` 跟踪状态
- 每次完成一项工作后，必须及时打勾更新
- 如果属于实施方案，完成开发与验证后，文件名必须改为 `YYYY-MM-DD-已完成-目的.md`
- 已完成的临时实施文档默认仅用于后续 bug 排查、回溯和核对，一般开发流程不继续读取
- 如果后续修复 bug 需要继续参考，仍应优先以正式开发文档为准，临时文档只作过程记录

## 8. 唯一守则

本项目在 `docs` 下只保留以下核心约束：

- 一份项目规则
- 一套开发文档体系
  - 一份索引主文档
  - 多份按功能/结构拆开的正式开发内容
- 一个 `docs/temp` 目录用于短期临时文档和清单式实施方案

除上述结构外，不应在 `docs` 内长期堆积无编号、无归属、无清理计划的杂散文档。
