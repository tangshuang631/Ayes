# 18 Web 工作台与人类测试界面

## 1. 文档目标

本文件定义 Ayes 下一阶段必须实现的本地 Web 工作台。

目标不是做宣传页，而是做一个：

- 人类用户可直接使用
- 可直接观察监控效果
- 可直接查看记忆、事件、日志
- 可直接测试问答与条件监控

的工作台界面。

## 2. 定位

Web 工作台是 Ayes 当前阶段的人类主入口。

它必须承担：

- 目标选择
- 监控任务配置
- 监控启动与停止
- 近期事件查看
- 短期记忆查看
- 问答测试
- 运行状态查看
- 日志查看入口

## 3. 布局原则

前端必须：

- 简洁
- 高信息密度
- 少卡片
- 强一体感

推荐结构：

1. 左侧：目标与任务区
2. 中间：近期事件时间线 / 当前截图预览 / 记忆查看
3. 右侧：问答区 / 日志区 / 状态区

页面应优先使用：

- 分栏
- 表格
- 列表
- 时间线
- 分割线
- 抽屉 / 折叠面板

不推荐：

- 卡片瀑布流
- 组件堆砌式 dashboard
- 营销页式大块留白

默认首屏应只保留最短人工核验链路需要的模块，低频排查面板应优先进入折叠区按需展开。

- 风格层应优先吸收以下特征：
  - 克制的黑白灰主色
  - 连续纸面感背景
  - pill 化按钮、输入框和筛选控件
  - 极少装饰、少阴影、细分割线
  - 通过字重、字号、边线和留白建立层级

不应照搬的部分：

- 营销型 hero
- 说明式首页排版
- 低信息密度的大段居中排版

## 4. MVP 必做界面模块

### 4.1 目标选择区

- 查看屏幕候选
- 查看进程候选
- 显示预览、进程名、代表窗口标题、可观测状态
- 点击绑定监控目标
- 对低分辨率辅助候选默认折叠，用户按需展开
- 支持像共享屏幕软件一样，优先通过预览图判断“是不是我想监控的对象”
- 进程级选择也必须显示代表性窗口快照，不能只显示进程名
- 不再单独铺设窗口候选主列表，避免与进程候选重复；如需单窗口监控，应在选定进程候选后切换到“监控当前窗口”模式

### 4.2 任务配置区

- 选择 observe / triggered
- 调整采样频率
- 配置关键词或简单触发条件
- 配置是否启用 webhook
- 配置是否启用 refresh_click
- 显示当前已绑定目标摘要
- 支持将当前界面配置直接转成 watch spec 并装载

### 4.3 运行控制区

- 启动监控
- 停止监控
- 显示运行中 / 已停止 / 异常
- 显示当前任务绑定目标
- 主视图区应保持简洁，不应堆叠大量统计盘
- 首屏默认定位为“当前原始读屏”，而不是“运行概览 dashboard”
- 优先直接展示当前任务、当前采集目标、最近采集状态，以及最近一次 OCR / 视觉辅助的原始摘要结果
- 首屏状态区还应直接展示“最近关键事件”摘要，至少包括摘要、时间、位置摘要和原始文本预览，避免用户必须滚动时间线才能判断当前是否真的读到了有价值的信息
- 对于变化频繁的监控任务，前端应更偏向展示“刚刚从目标读到了什么”，而不是长期固定的聚合统计数字
- 需要更详细统计时，用户应通过事件、日志、短期记忆和问答面板自行核验，而不是把这些统计全部堆在首屏
- 当前实现应移除单独的状态统计盘容器，首屏状态区默认只保留原始读取摘要、运行元信息和可展开核验的原始状态 JSON
- 其中运行元信息应尽量直接显示当前任务快照，包括模式、目标类型、采样频率、ROI 数量、视觉/告警/刷新点击开关，而不是只显示一串通用运行状态
- 运行元信息还应直接给出监控活跃度判断，例如“最近仍有新事件 / 最近执行过但暂无新事件 / 长时间未执行需检查”，避免用户自己阅读时间戳后再推断链路是否停滞
- 首屏不得再次引入“统计总览”“监控总数”“命中计数”“面板式 KPI”等与当前任务弱相关的信息块；如果任务切换后这些数字无法直接帮助判断当前是否读对，就不应放在首屏
- 首屏状态区中每一行都应尽量来自当前目标的最近原始读取、最近事件或当前任务快照，而不是来自额外计算出的装饰性统计
- 原始状态 JSON 仍应保留，但默认应下沉到折叠区，不应抢占首屏主要注意力
- 用户打开页面后，默认首先看到的应是“这个目标刚刚读到了什么”，然后才是“完整运行状态长 JSON”
- 如果当前状态已具备最近 OCR 块级结构，则首屏应直接展示少量块级原始数据，至少包括块文本、方向、置信度和 `rect_norm`
- 如果当前已具备最近截图路径与块级坐标，首屏还应直接给出一张小型证据图叠框，帮助人工立刻核对“这段 OCR 是从画面的哪一块读出来的”
- 对 `process` 目标，运行状态区和截图区都应尽量直接说明“最近真正捕获到的是这个进程下的哪一个窗口”，至少包括 `process_name / window_title / window_id / window_state`
- 运行元信息中还应直接显示 `后台持续监控: 是/否`、`前端连接数` 和 `最近捕获目标`，避免用户只能通过展开原始状态 JSON 才知道后台是否真的还在运行
- 截图区的标题摘要应优先使用“最近实际捕获目标”而不是仅使用配置目标；如果配置目标与实际捕获目标不同，应同时展示两者
- 截图区还应直接显示最近采集状态，例如 `ok / failed / metadata_only`，避免用户只能从运行状态区间接推断截图是否来自最新成功采样
- 当后台持续监控已启动时，首屏状态区、当前截图区、近期事件区、OCR 片段区和最近记忆条目区应按同一轮询节奏同步刷新
- 不要求在后台轮询中每次都自动重跑问答结果，但至少不能出现“状态已更新而截图和最近记忆仍停留在旧轮次”的明显错位

### 4.4 近期事件区

- 展示最近事件时间线
- 支持查看事件类型、时间、摘要、目标、优先级
- 支持查看 OCR 文本摘要
- 首屏运行状态区中的 OCR 摘要应优先展示最近一次原始读取文本，以及少量块级文本预览和大致位置方向，便于人工快速判断“有没有读对、读到哪里”
- 支持查看 OCR 质量摘要，至少包括 provider、字符数、块数、平均置信度和是否稀疏
- 如果事件包含块级位置结构，应直接显示区域名和大致位置摘要，而不是只暴露原始 bbox
- 近期事件区默认应保持展开，用于优先回答“刚刚发生了什么”

### 4.5 短期记忆区

- 展示最近几分钟的结构化记忆
- 支持按关键词过滤
- 支持按最近 N 分钟过滤
- 在问答命中证据事件中，如果已具备位置摘要，应直接用于人工核验
- 除问答结果外，还应直接显示“最近记忆条目”列表，让用户在不提问时也能查看最近几分钟内被保留下来的关键事件
- 最近记忆条目应尽量复用事件时间、摘要、位置摘要和证据预览，而不是单独发明另一套不可核验的数据格式

### 4.6 问答区

- 输入问题
- 返回结构化回答
- 显示命中事件与证据引用
- 显示使用的时间范围
- 如果问题命中了数值或规则类事件，问答区应直接显示结构化命中摘要，例如：
  - 命中字段
  - 命中值
  - 单位
  - 命中规则
  - 区域名称
  - 人类可读时间

要求：

- 用户不应必须展开原始事件 JSON 才能看懂“到底命中了什么”
- 问答区的结构化摘要应优先服务人工核验和后续 Agent 消费
- 问答区应提供少量快速提问入口，例如“最近几分钟发生了什么”“最近几分钟有命中或告警吗”“最近几分钟有没有异常”，帮助用户直接完成最小人工闭环核验
- 问答输入区附近还应直接显示当前核验上下文，例如最近 OCR 内容、最近关键事件和当前时间范围，帮助用户围绕同一批证据继续追问
- 问答区应直接提供当前截图核验参考，至少能看到当前画面缩略图与 ROI 提示，避免用户提问时脱离当前正在看的那张图
- 问答区还应基于当前 OCR 内容或最近关键事件给出少量继续追问建议，帮助用户围绕同一批近期证据快速深入，而不是每次重新组织问题
- 问答结果区应先给出命中证据事件的简短摘要列表，再展示下方时间线明细，帮助用户快速建立“这次回答主要依据了哪几条事件”的整体印象
- 证据事件摘要列表应支持直接定位到下方对应事件明细，减少用户在多个相似事件之间来回比对
- 如果已存在可读时间和区域信息，应直接在问答摘要区展示，而不是只埋在下方事件明细中
- 如果命中了 vision 事件，问答区应额外显示视觉结构化摘要，包括视觉摘要、细节行、触发原因、模型名和区域信息，而不是只把这些信息埋在事件明细里
- 问答结果摘要区还应直接显示“首条证据时间”和“当前截图参考时间”，帮助用户立刻判断“这次回答依据的是不是我眼前这一轮画面”
- 工作台应提供一个共享证据查看区，允许从近期事件或问答证据中点击选中某条证据，并在固定位置查看更大的截图、时间、目标和位置摘要，减少用户在多个缩略图之间来回比对

### 4.7 日志区

- 查看系统日志
- 查看监控任务日志
- 查看 OCR / capture / diff / alert 相关日志
- 查看 vision 相关触发与跳过原因
- 支持按日志类别过滤
- 支持按当前任务或指定任务查看
- 日志区默认应置于折叠区，避免与首屏原始读屏和问答核验链路竞争注意力

### 4.7.1 视觉轨迹区

- 单独查看 `vision_triggered` / `vision_skipped` 事件
- 直接显示触发原因、阻断原因、模型名、provider 和相关证据
- 如果视觉模型返回了多行结果，应尽量保留前几条细节行，而不是压扁成只有一句摘要
- 用于人工判断“为什么这次启用了视觉增强”以及“为什么当前轮次没有启用”
- 视觉轨迹、动作轨迹、命中轨迹、告警轨迹和 OCR 片段都属于排查型面板，默认应折叠收纳

### 4.8 任务与时间范围区

- 可显式输入或切换任务 id
- 可设置最近 N 分钟范围
- 该时间范围必须实际作用于近期事件、问答与短期记忆读取
- 用户问“最近几分钟发生了什么”时，界面和接口都应遵守当前时间范围

## 5. 当前阶段验收要求

只有当以下内容成立时，Web 工作台才算达标：

- 用户无需命令行也能完成一次目标选择和监控启动
- 用户能直接看到近期事件
- 用户能直接看到短期记忆
- 用户能直接发起一次问答
- 用户能直接查看近期日志

当前实现还应至少包括：

- 当前截图预览
- 当前截图预览上的已启用 ROI 叠框
- 运行状态面板
- 屏幕目标一键加载
- 进程目标点击加载
- 一次执行采样按钮
- 停止监控按钮
- 最小任务配置表单

## 6. 与后续 Agent 接入的关系

Web 工作台只是人类入口。

它背后的监控、查询、日志和问答能力必须继续保持服务化边界，供后续：

- skill
- tool
- MCP
- agent

复用。

## 7. 当前实现校准

当前代码已落地第一版本地 Web 工作台：

- [web/static/app.css](/Users/apple/Desktop/2026/Ayes/web/static/app.css)

- [src/ayes/api/server.py](/Users/apple/Desktop/2026/Ayes/src/ayes/api/server.py)

当前已验证可用的页面链路：

- 加载屏幕监控任务
- 加载窗口监控任务
- 执行一次监控采样
- 查看近期事件
- 查看问答与短期记忆
- 查看近期日志
- 查看当前截图预览

这意味着当前阶段已经不再只有 CLI，而是具备了可直接人工测试的本地工作台入口。

当前数据来源也已从纯内存态开始过渡为：

- 当前运行状态：服务内状态
- 近期事件：SQLite + 当前任务读取
- 近期日志：SQLite + 当前任务读取
- 问答与短期记忆：当前短期记忆查询接口

后续仍需继续推进长期记忆和更多筛选能力，但工作台已经具备真实服务化读取链路。

当前工作台还新增了：

- 任务 id 输入框
- 最近 N 分钟时间范围输入
- 长期摘要视图
- 屏幕候选与进程候选双列表
- 最小 watch spec 配置区

这使得工作台开始具备：

- 显式任务切换准备
- 显式时间范围切换准备
- 长期/短期双层查看入口

后续这几个入口不能只停留在“有输入框”，而必须满足：

- 任务 id 切换后，近期事件、长期摘要、日志、问答都能按任务读取
- 最近 N 分钟切换后，近期事件和问答都能按时间范围收敛
- 问答结果应显示回答、命中证据、使用时间范围与记忆层
- 近期事件、OCR 片段、动作轨迹、命中轨迹、告警轨迹、长期摘要、日志区都应显式显示当前查询上下文，例如 `task_id / minutes / source|category / count`
- 长期摘要区还应支持显式 `hours` 范围输入，便于人工核验“最近 24 小时 / 48 小时 / 72 小时”的长期回顾链路，而不是只能看不带时间范围的最近摘要列表
- 当某个面板在当前过滤范围下没有结果时，界面应直接说明“当前范围内无结果”，而不是只留下空白列表

当前阶段下一批必须落地的能力：

- 目标选择区显示屏幕候选与进程候选两类对象
- 工作台提供最小 watch spec 配置面
- 用户无需命令行即可完成“选目标 -> 配置模式/频率/关键词 -> 装载任务 -> 执行一次”

目标切换补充要求：

- 当用户从一个屏幕/进程/窗口切换到另一个目标时，前端不得继续静默沿用上一个目标的 ROI 草稿
- 如果当前 ROI 来自旧目标，则应在切换时清空 ROI 编辑区、区域 JSON 和预览状态，避免把旧坐标误绑定到新目标
- 只有当用户重新载入当前目标预览并重新框选后，新目标的 ROI 才应进入待装载状态
- 对同一目标的重复点击可保留当前草稿；但跨目标切换默认应视为新的绑定上下文
- 跨目标切换时，任务配置区也不得继续静默沿用上一目标的 `mode / query / sampling / vision / alert / refresh_click`
- 默认应回到安全初始配置，例如 `observe`、空查询、基础采样频率、关闭视觉辅助、关闭告警、关闭刷新点击
- 仅任务范围类字段可保留，例如当前 `task_id`、问答时间范围、长期摘要小时范围
- 这样用户在切换目标后会明确看到“现在要重新定义这个目标要怎么监控”，而不是把旧任务条件误装到新目标上

当前实现校准补充：

- 已新增 `/api/targets`，统一返回屏幕候选和进程候选；如有需要，后端仍可保留窗口级元数据供 `window` 模式装载使用
- 已新增 `/api/watch/load-configured`，允许 Web 表单直接生成并装载 watch spec
- 当前工作台已支持“选主屏幕 -> 配置 observe/triggered、频率、关键词、webhook -> 装载任务 -> 执行一次”

当前阶段仍需继续补齐并应视为正式要求的能力：

- 用户无需命令行即可启动持续监控
- 工作台应明确区分“已装载任务”和“后台持续运行中”
- 停止按钮应能停止持续监控，而不是只清空当前任务状态

当前实现补充：

- 工作台已新增 OCR 片段区，用于直接查看最近识别文本，辅助配置 triggered 关键词
- 告警轨迹不再只是空容器，后端已开始生成真实的 `alert_sent` / `alert_failed` / `alert_suppressed` 事件
- 这意味着用户已经可以通过界面观察“最近识别到了什么文本”以及“是否真的尝试过发送告警”
- 工作台运行状态区当前应直接显示最近一次 OCR 摘要、最近视觉辅助判断和最近视觉补充结果，便于直接看出“刚刚读到了什么”
- 运行元信息仍保留任务 id、运行状态、最近执行和最近错误等文字摘要，供人工快速核验
- 当前阶段不应在首屏继续堆叠统计盘；命中、告警、记忆、日志等聚合信息主要通过对应面板查看
- 当前截图预览区应直接叠加当前任务已启用 ROI，用户无需切回左侧框选区也能确认“当前到底在盯哪几块区域”
- 问答区已新增结构化摘要展示，直接显示结论、置信度、实际命中时间范围、证据事件数量和记忆层
- 近期事件、OCR 片段和问答证据事件应逐步直接展示 `区域 / 大致方位` 级别的位置摘要，降低人工核对 bbox 的成本
- 近期事件、OCR 片段、动作轨迹、命中轨迹、告警轨迹、长期摘要、近期日志等列表，当前已开始显式显示 `task_id / 时间范围 / 来源或类别 / 条数`，并在空结果时直接解释当前过滤上下文
- 问答与短期记忆区当前已新增“最近记忆条目”列表，可按当前任务、最近时间范围和关键词直接查看近期保留事件
- OCR 相关事件当前已开始附带轻量质量摘要，帮助用户快速判断“是否真的识别到了足够可靠的文本”
- 当视觉增强启用时，时间线中当前已开始出现 `vision_triggered` / `vision_skipped` 事件，帮助用户直接判断“为什么这次触发了视觉增强，或为什么没有触发”

## 8. 当前人工测试步骤

当前版本可按以下步骤直接人工测试：

1. 启动本地服务并打开工作台首页
2. 在左侧“监控目标”中点击主屏幕或某个进程候选
3. 在“任务配置”中选择 `observe` 或 `triggered`，设置截图/OCR 频率并装载任务
4. 点击“执行一次”或“开始持续监控”
5. 在中间区域查看：
   - 当前截图预览
   - 近期事件
   - OCR 片段
   - 命中轨迹 / 告警轨迹
6. 在右侧输入“最近发生了什么”或关键词问题，检查：
   - 是否返回结构化结论
   - 是否显示时间范围
   - 是否显示证据事件
   - 是否显示记忆层
   - 是否显示“最近记忆条目”列表
7. 切换日志类别或任务范围，检查近期日志、近期事件和问答是否随之变化
