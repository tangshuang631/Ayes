# 17 监控目标选择交互

## 1. 文档目标

本文件定义 Ayes v1 的监控目标选择交互。

目标是让用户像使用共享屏幕软件一样，通过预览画面直接选择：

- 整个屏幕
- 指定进程下的业务窗口

## 2. 交互目标

目标选择交互必须满足：

- 用户不需要理解系统窗口结构
- 用户不需要直接操作进程 id 或窗口 id
- 用户可以通过预览画面判断自己要监控什么
- 用户可以快速看出哪些目标当前可观测
- 用户可以一眼区分整个屏幕和窗口目标

## 3. 候选目标来源

候选目标列表由以下两类组成：

- 屏幕候选
- 进程候选

### 3.1 屏幕候选

每个屏幕候选至少显示：

- 屏幕预览图
- 屏幕名称或编号
- 分辨率
- 当前是否可采集

### 3.2 进程候选快照

当用户希望“监控该进程”而不是只监控一个窗口时，界面不能只显示进程名。

至少应显示：

- 该进程当前代表性窗口的快照
- 进程名
- 代表性窗口标题
- 分辨率
- 当前可观测状态

如果进程当前没有可用代表快照，也应保留候选，但默认放入折叠区，避免误导用户。

## 4. 列表排序

进程候选应优先按业务价值排序，而不是按系统返回顺序原样展示。

建议排序优先级：

1. 当前可观测且有代表画面的业务进程
2. 当前可观测但标题不清晰的进程代表窗口
3. 不可观测但仍保留元数据的进程候选
4. 明显辅助或装饰性进程候选

## 5. 过滤规则

目标选择界面默认应隐藏或弱化以下对象：

- 极小的辅助窗口
- 明显无画面的窗口
- 装饰性窗口
- 重复或无业务意义的系统附属窗口

但如果用户显式切换到“显示全部”，可以展示完整候选集合。

### 5.1 默认折叠规则

第一阶段默认增加以下折叠规则：

- `width <= 500` 且 `height <= 500` 的进程代表窗口候选，默认进入“低分辨率/辅助候选”折叠区
- 没有可用代表快照的进程候选，默认进入折叠区

用户可以手动展开折叠区查看完整列表，但默认主视区应优先显示：

- 有快照
- 当前可观测
- 分辨率较大
- 更像主业务窗口或主业务进程

的目标。

## 6. 候选目标卡片信息

每个候选项建议统一显示：

- 预览图
- 主标题：进程名或屏幕名
- 副标题：代表窗口标题、目标类型、分辨率或状态
- 可观测状态标记
- 是否推荐选择标记

补充要求：

- 屏幕候选必须显示真实屏幕快照
- 进程级选择应显示代表性窗口快照
- 如果快照缺失，应默认折叠或弱化，而不是与主候选完全等权混排

## 7. 可观测状态标记

第一阶段至少需要显示以下状态：

- `可观测`
- `部分可观测`
- `仅有元数据`
- `当前不可采集`

作用：

- 帮助用户理解为什么某些窗口不能稳定监控
- 降低最小化、后台、辅助窗口造成的误解

## 8. 绑定流程

### 8.1 屏幕绑定

1. 用户选择某个屏幕候选
2. 系统生成 `target.type = screen`
3. 写入对应 `screen_id`
4. 进入 watch spec 配置或监控启动流程

### 8.2 当前窗口绑定

1. 用户选择某个进程候选
2. 系统读取该候选当前代表窗口、对应进程、可观测性信息
3. 用户在任务配置区选择“监控当前窗口”
4. 系统生成 `target.type = window`
4. 进入 watch spec 配置或监控启动流程

### 8.3 进程绑定

如果用户希望“盯住这个软件”，而不是只盯一个窗口，则：

1. 用户从进程候选中选择某个业务进程
2. 系统提供“只监控当前窗口”与“监控该进程相关业务窗口”两种后续选项
3. 如果选择进程级监控，则生成 `target.type = process`

运行时语义补充：

- `process` 级监控在每个采样 tick 会重新解析该进程当前最优的代表业务窗口
- 当前工作台应把它理解为“盯住这个软件当前最值得看的主画面”，而不是“同时拼接所有窗口”
- 如果当前没有可采集业务窗口，状态区和日志区必须明确提示，而不是退回整屏继续采样
- 如果代表业务窗口发生切换，时间线和日志区应尽量产生显式切换事件，帮助用户理解“当前仍在同一进程下，但观察对象已经换窗”

## 8.4 ROI 框选流程

v1 正式支持在已选目标上继续框选多个监控区域。

流程：

1. 用户先选择 `screen / window / process`
2. 系统展示对应目标的当前预览图或虚拟画布
3. 用户在该画面上框选一个或多个 ROI
4. 每个 ROI 至少填写或自动生成一个名称
5. 系统将 ROI 写入 `watch spec.target.regions`
6. 任务启动后，OCR、变化检测和视觉增强优先围绕这些 ROI 执行

交互要求：

- 支持鼠标拖拽框选
- 支持删除、重命名和开关单个 ROI
- 支持显示每个 ROI 的边框和名称
- 支持用户不框选，直接监控整个目标
- 支持在同一目标预览图上连续添加多个 ROI
- 前端应直接维护结构化 ROI 列表，并与任务配置联动

第一阶段不要求：

- 任意多边形
- 旋转框
- 像素级分割

第一阶段只要求稳定的矩形多 ROI

当前阶段实现要求补充：

- 不应只让用户手写 ROI JSON
- 工作台应提供基于预览图的直接框选入口
- JSON 结构可以保留为高级调试入口，但不应成为主要操作方式

## 9. 与受控刷新点击的关系

当用户后续配置 `refresh_click` 时：

1. 必须先有已绑定的窗口或屏幕目标
2. 基于当前目标展示预览图
3. 用户在该预览图上选择点击点

因此目标选择交互和刷新点击交互必须共用同一套预览与坐标体系。

补充要求：

- ROI 框选、刷新点击点选和后续证据标注应共用同一坐标体系
- 问答和事件展示时应尽量能说明变化发生在哪个 ROI
- 对 `process` 目标，若代表窗口发生切换，ROI 继续绑定到最新代表窗口画面的 `target` 坐标系；工作台应尽量通过事件、日志或状态提示暴露该切换语义

## 10. 与隐式上下文问答的关系

监控目标一旦绑定成功，后续问答就默认带入该目标。

这意味着目标选择交互不仅决定采集对象，也决定后续：

- 问答上下文
- 告警上下文
- 刷新点击上下文

## 11. 第一阶段结论

目标选择交互必须以预览画面为中心，而不是以底层 id 为中心。

它的本质是把系统级窗口和屏幕对象，转换成用户能直观看懂、能直接点击绑定的监控目标。

## 12. 当前阶段实现约束

考虑到第一阶段先强调“可人工核验”和“尽快形成可用工作台”，当前阶段允许采用以下渐进式实现：

- 屏幕候选必须提供真实预览图
- 进程候选应优先补齐真实预览图
- 若某类候选暂时没有稳定快照，也不能直接与主候选混排，必须默认折叠并清晰标注
- 对进程候选，应继续保留后续更稳定独立预览图的 API 边界

当前阶段最低要求：

- 屏幕候选和进程候选在同一工作台中可见
- 用户点击屏幕或进程候选后，必须进入统一的任务配置区
- 任务配置区应能明确显示当前绑定目标
- 任务配置保存后，应能直接装载对应 watch spec 并进入运行控制链路

## 13. 当前交互收口结论

当前工作台正式收口为：

- 主选择列表只展示“屏幕候选”和“进程候选”
- 不再单独铺设“窗口候选”主列表
- `window` 仍然是正式支持的监控目标类型，但其入口改为：
  - 用户先选择某个进程候选
  - 再在任务配置区切换为“监控当前窗口”

这样处理的原因：

- 进程候选已经包含代表窗口快照、标题和分辨率
- 单独窗口候选列表会与进程候选高度重复
- 对人类用户来说，先判断“是不是这个软件/这张画面”比直接理解窗口层级更自然
- 保留 `window / process` 双模式即可兼顾“只盯当前窗口”和“盯住整个软件”的两类需求
