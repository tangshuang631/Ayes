# 08 技术选型与运行形态

## 1. 第一阶段运行形态

第一阶段固定为：

> 本地常驻服务 + 本地 CLI / HTTP 接口

不做桌面 UI 作为第一优先。

原因：

- 第一阶段重点在采集、时间线、问答和告警
- 先把服务能力跑通，比先做 UI 更重要
- 后续无论接 skill、MCP 还是桌面前端，都需要稳定本地服务作为底座

## 2. 第一阶段推荐语言

第一阶段推荐主语言为：

> Python

原因：

- OCR、文本处理、embedding、HTTP、规则引擎、时间线存储都适合 Python 快速落地
- 适合做本地守护进程、CLI 和事件处理链路
- 后续接模型、向量匹配、告警和测试成本较低

## 3. 系统 API 接入方式

在 macOS 环境下，窗口发现和窗口采集优先采用：

- `PyObjC`
- `Quartz`
- `AppKit`
- 必要时接 `Vision`

原因：

- Ayes 第一阶段目标是指定进程全窗口监控
- 这要求直接访问系统窗口元数据和截图接口
- Python 主体下接系统原生框架，比一开始单独写 Swift 服务更快

## 4. OCR 方案

第一阶段 OCR 的设计原则是：

> OCR 能力必须跨平台抽象，首个落地实现可以先使用当前平台最稳的后端。

第一阶段推荐做法：

1. 定义统一 OCR Provider 接口
2. 在当前 macOS 环境下先接一个可用实现
3. 后续补 Linux / Windows 可替换 Provider
4. 上层事件抽取、语义匹配、问答逻辑只依赖 OCR 抽象结果，不依赖具体引擎

推荐顺序：

1. 先评估跨平台 OCR 引擎作为默认方案
2. 若默认方案在当前环境效果或性能不足，再补平台专属 Provider

这样选的原因：

- 你明确要求后续 skill 具备跨平台能力
- skill 的核心能力不能绑死在 macOS 原生 API 上
- 第一阶段可以先在 macOS 上验证链路，但接口必须天然支持替换

### 4.1 OCR 候选结论

当前优先级建议如下：

1. `PaddleOCR`：作为第一优先候选
2. `RapidOCR`：作为轻量和部署便利方向的备选
3. `Tesseract`：作为兼容性兜底方案，不建议作为主路线

初步判断依据：

- `PaddleOCR` 官方项目明确支持多语言和 Agent / RAG 场景，适合结构化输出与后续演进
- `RapidOCR` 强调多平台、离线、速度和兼容性，适合作为轻量备选
- `Tesseract` 跨平台成熟，但对复杂现代 UI 文本、混合布局和中文场景通常不是最优主选

因此当前正式建议是：

> 第一阶段优先按 `PaddleOCR Provider` 设计，必要时保留 `RapidOCR Provider` 和 `Tesseract Provider` 的替换位。

## 4.2 非文本视觉增强方案

对于图片、图标、图表、颜色状态和弹窗形态等 OCR 不擅长的内容，Ayes 允许引入本地小型视觉模型作为增强层。

正式定位：

- 不替代 OCR Provider
- 不替代变化检测和事件抽取
- 作为可选 `vision enhancer` / `visual tagger` 层补充结构化信息

推荐策略：

1. 默认不全量启用
2. 仅在需要图像理解的监控任务中按配置启用
3. 仅在差分明显、OCR 低置信度或用户明确要求时触发
4. 输出必须收敛为统一标签、属性或事件，不允许把大段原始模型输出直接灌入主链路

第一阶段结论：

- 先把跨平台 OCR 主链路做稳
- 小型本地视觉模型作为第二优先增强能力预留接口
- 不把 YOLO 作为当前 MVP 的默认中心

## 5. 语义匹配方案

第一阶段语义匹配采用：

> 本地 embedding + 小规模最近事件相似度检索

第一阶段不引入重型独立向量数据库。

原因：

- 只保留最近 5-15 分钟事件，数据量本身很小
- 可以先用本地存储加内存计算完成相似度检索
- 先把检索语义跑通，比提前上复杂向量基础设施更重要

## 6. 向量与事件存储

第一阶段推荐存储为：

> SQLite 作为主存储

用于保存：

- watch 配置
- 窗口元数据
- 事件记录
- OCR 文本
- embedding 向量引用或序列化结果
- 告警记录
- 长期轻量摘要事件

证据截图或切片不建议直接塞进数据库正文，可采用：

- 文件落盘
- 数据库只保存引用路径或 evidence id

时间线存储建议分层：

- 短期详细层：保留最近 5-15 分钟的细节事件
- 长期轻量层：保留更长时限的摘要事件和关键状态

## 7. 企业微信推送方案

第一阶段告警采用：

> 企业微信 webhook HTTP 推送

这是第一阶段默认且唯一标准告警出口。

## 8. 推荐模块划分

第一阶段运行时建议拆成以下逻辑模块：

- `watcher`：进程与窗口发现
- `capture`：采样与截图
- `detector`：差分与 ROI 检测
- `ocr`：OCR 与文本清洗
- `tagger`：轻量视觉标签
- `matcher`：语义匹配
- `timeline`：事件存储与检索
- `alerter`：企业微信告警
- `api`：CLI / HTTP 接口

## 10. 第一阶段技术选型结论

第一阶段默认技术栈结论如下：

- 主语言：Python
- 运行形态：本地常驻服务 + CLI / HTTP
- 系统接入：PyObjC + Quartz/AppKit
- OCR：跨平台 Provider 抽象优先，第一候选为 PaddleOCR Provider
- 语义匹配：本地 embedding + 最近事件相似度检索
- 主存储：SQLite
- 证据存储：本地文件 + 数据库引用
- 告警：企业微信 webhook

这是当前正式开发依据。

## 10.1 本地服务与前端进程关系

第一阶段本地服务与前端 Web 工作台必须解耦。

要求：

- 监控一旦启动，即使前端页面关闭，后台监控也应继续运行
- 只有用户显式在前端停止监控，或当前根本没有监控任务在运行时，退出前端才允许整体退出后台服务
- 不允许把“浏览器页面是否还开着”当成监控是否继续运行的唯一依据

这意味着：

- Ayes 需要本地后台服务进程
- Web 工作台只是连接该后台服务的人类入口
- 后续 Agent / skill 也应连接同一后台服务，而不是依赖前端页面常驻

## 10.2 桌面启动器要求

第一阶段应提供一个桌面可点击启动入口。

启动行为要求：

- 启动时先检查当前是否已有 Ayes 后台进程
- 如果已有后台进程，则直接拉起前端页面并用默认浏览器连接
- 只有在后台不存在 Ayes 进程时，才从头启动后台服务
- 不允许重复启动多个 Ayes 后台实例

这意味着桌面启动器必须默认按“单实例后台 + 可重复打开前端”的方式工作。

## 10.3 当前阶段服务生命周期实现约束

当前阶段允许后台服务在空闲时自动退出，但必须满足以下约束：

- 监控运行中时绝不自动退出
- 仅前端断开连接并不能直接杀死正在运行的监控
- 自动退出应建立在“无监控运行 + 无前端连接 + 空闲超时”三条件同时满足之上
- 生命周期控制必须优先保证单实例和稳定性，不能为了自动退出牺牲服务可达性

如果自动退出实现不稳定，则当前阶段应优先退回为：

- 后台稳定常驻
- 由显式停止或独立脚本回收

先保证可用，再补更细的自动回收。

## 10.4 当前启动器实现校准

当前代码已开始把桌面启动器链路收口为“薄 shell + Python 服务控制模块”：

- [scripts/start_ayes_service.sh](/Users/apple/Desktop/2026/Ayes/scripts/start_ayes_service.sh)
- [src/ayes/app/service_control.py](/Users/apple/Desktop/2026/Ayes/src/ayes/app/service_control.py)
- [src/ayes/cli/launcher.py](/Users/apple/Desktop/2026/Ayes/src/ayes/cli/launcher.py)

当前实现约束：

- shell 脚本只负责补齐基础环境并转交 Python 启动入口
- 单实例判断、PID 清理、健康检查、空闲监控启动等关键逻辑统一放在 Python 侧
- 如果 PID 仍存活但健康检查失败，当前实现会拒绝重复拉起第二个后台实例，而不是静默叠加多进程
- 若当前服务已健康运行，启动器只复用已有实例并重新打开前端页面

这样做的原因：

- 桌面、提权 shell、Codex shell 的环境差异较大
- 关键生命周期逻辑放在 bash 中不利于测试，也不利于后续扩展
- 统一到 Python 侧后，可以直接用 pytest 验证单实例和启动判定逻辑

当前桌面交付入口补充：

- [scripts/build_launcher_app.sh](/Users/apple/Desktop/2026/Ayes/scripts/build_launcher_app.sh) 当前会调用 Python launcher 构建 `Ayes 启动器.app`
- 构建产物会先生成到 `runtime/Ayes 启动器.app`
- 当前脚本默认会同时安装到桌面 `~/Desktop/Ayes 启动器.app`
- 当前实现不再依赖 AppleScript 编译 `.app`，而是直接生成原生 macOS App bundle（`Contents/Info.plist` + `Contents/MacOS/AyesLauncher`）
- `AyesLauncher` 只负责无终端地拉起 `scripts/start_ayes_service.sh`，单实例判断和前端复用仍统一走 Python 服务控制链路
- 该方案已在当前环境完成真实构建验证，避免 AppleScript 语法和系统环境差异导致的编译不稳定问题

这意味着当前阶段已经开始具备“本地构建 -> 安装桌面启动入口 -> 点击复用后台并打开前端”的交付形态。

## 11. 最新实现校准

截至当前代码版本，第一阶段还新增了两项已验证的最小实现结论：

### 11.1 窗口采集能力分级

macOS 当前不应把“窗口可枚举”直接等同于“窗口可截图”。

当前真实抽样显示：

- `onscreen = true` 的窗口更可能抓图成功
- `onscreen = false` 的窗口即使有元数据，也大量返回 `no_pixels`

因此运行时必须把窗口采集能力分成：

- `recommended`
- `best_effort`
- `metadata_only`

### 11.2 变化检测先走轻量链路

第一阶段当前已正式采用：

- `SamplingTicker` 统一调度截图 / OCR / 差分节拍
- `MacOSScreenCapture` 作为首个可运行 capture 实现
- `ByteDiffDetector` 作为最小变化检测器

这意味着当前技术路线不是一开始就上复杂视觉模型，而是先建立：

- 可稳定调度的采样层
- 可验证的统一帧结构
- 可控的“无变化跳过 OCR”前置判定
