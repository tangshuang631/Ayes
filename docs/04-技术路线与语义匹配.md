# 04 技术路线与语义匹配

## 1. 第一阶段固定路线

第一阶段固定采用：

> OCR + 向量语义匹配 + 轻量视觉标签

## 2. 为什么当前不以 YOLO 为主线

第一阶段核心问题是：

- 过去几分钟发生了什么
- 哪些变化值得关注
- 哪些变化应触发告警
- 当前界面为什么会变成这样

这些问题在第一阶段更依赖：

- OCR 文本变化
- 窗口标题变化
- 区域内容变化
- 轻量标签
- 时间顺序

因此 YOLO 不是 MVP 的基础能力。

## 3. OCR 层职责

OCR 层负责：

- 提取变化区域文字
- 提取标题、正文、按钮文案、数值和表格片段
- 进行清洗、分块和归一化
- 将 OCR 文本与窗口、区域、时间绑定

第一阶段虽然先在 macOS 环境落地，但 OCR 层必须按跨平台抽象设计，不能把上层逻辑直接绑定到某个系统专属 OCR API。

## 4. 轻量视觉标签

第一阶段采用轻量标签，而不是复杂检测模型。

建议标签包括：

- `dialog`
- `error_like`
- `status_change`
- `form_change`
- `table_delta`
- `notification_like`
- `captcha_like`

标签来源可以包括：

- OCR 关键词
- 规则判断
- 区域变化形态
- 窗口结构信号

## 5. 语义匹配职责

语义匹配层负责：

- 对事件文本、摘要、标题、标签做 embedding
- 对监控意图做 embedding
- 判断事件是否命中重点关注内容
- 支持基于语义的问题检索最近时间线

## 6. 用户自然语言到 Watch Spec

用户可以自然语言描述要关注的变化，但 Ayes 不直接执行自然语言。

推荐流程：

1. 用户输入自然语言监控目标
2. 上层 Agent 或配置编译器转换为 `watch spec`
3. Ayes 根据 `watch spec` 执行

## 7. 第一阶段结论

第一阶段以：

- 规则
- OCR
- embedding 检索
- 轻量标签

作为主识别链路。

YOLO 放入第二阶段增强项。

## 8. 第一阶段最小采样与变化检测链路

当前代码层已经落地第一版最小链路：

- `screenshot tick`
- `screen capture`
- `byte diff detector`

对应实现文件：

- [src/ayes/capture/ticker.py](/Users/apple/Desktop/2026/Ayes/src/ayes/capture/ticker.py)
- [src/ayes/capture/screen.py](/Users/apple/Desktop/2026/Ayes/src/ayes/capture/screen.py)
- [src/ayes/detect/diff.py](/Users/apple/Desktop/2026/Ayes/src/ayes/detect/diff.py)

第一阶段先采用保守路线：

1. 用 `SamplingTicker` 控制截图、OCR、差分三个节拍
2. 先拿到统一 `CaptureFrame`
3. 先做轻量字节级差分，判断是否值得继续进入 OCR
4. 后续再补 ROI 检测、区域级去重和更细的视觉标签

这条链路当前不追求最终精度，目标是先稳定建立：

- 统一上游输入
- 可调采样频率
- 变化触发 OCR 的基本门槛
- 后续 OCR / tagger / matcher 的可复用接口
