# Ayes 开发文档 v1.0

## 1. 项目定位

Ayes 是一个面向人类用户和 AI Agent 的视觉时序回放引擎。

它的核心目标不是“看当前屏幕”，也不是“全量做 OCR”，而是：

- 持续监控指定目标
- 识别有价值的视觉变化
- 将变化压缩为结构化事件
- 保留短时可查询时间线
- 支持人类用户和 Agent 对最近几分钟发生的事情进行提问

第一阶段，Ayes 首先服务于人类用户自己提问回放；后续再向 OpenClaw、Codex、MCP、各类 Agent 的 skill / tool 形态演进。

一句话定义：

> Ayes 是一个给 AI 和人类都能使用的“屏幕事件时间线系统”，负责把界面变化转换为可回放、可检索、可提问的结构化视觉记忆。

## 2. 第一优先场景

当前唯一最高优先的监控对象是：

> 指定进程下的所有窗口。

包括但不限于：

- 主窗口
- 子窗口
- 弹窗
- 新开窗口
- 后台窗口
- 被遮挡窗口
- 折叠窗口
- 最小化窗口

目标是尽可能覆盖这些窗口的可观测变化，而不是只监控当前前台可见窗口。

## 3. 核心用户价值

对于人类用户，Ayes 第一版要解决的问题是：

- 我想长期盯一个进程，但不想人工一直盯着
- 我想知道刚才 5-15 分钟内到底发生了什么
- 我想按自然语言定义“什么变化值得关注”
- 当重要变化出现时，我希望自动推送到企业微信
- 我想直接提问：“刚才这个进程为什么变成现在这样？”

对于未来 Agent 形态，Ayes 提供的是：

- 面向窗口/进程的视觉时间线
- 可检索的结构化事件流
- 可供 skill/tool 直接消费的上下文接口

## 4. 正确产品边界

Ayes 第一阶段不是以下产品：

- 不是通用桌面自动化平台
- 不是全能视觉大模型
- 不是传统录屏软件
- 不是纯 OCR 工具
- 不是全桌面无差别记忆系统

Ayes 第一阶段要做的是：

- 面向指定进程
- 面向短时历史
- 面向重要变化
- 面向回放与提问
- 面向结构化事件输出

## 5. 产品原则

- 先锁定监控目标，再做采集
- 先检测变化，再做重识别
- 先抽事件，再做问答
- 先服务人类用户回放，再封装成 Agent skill
- 默认保留短时高价值时间线，不做无限制全量存储
- 默认增量处理，避免高频全量 OCR
- 能结构化就不返回长段自然语言
- 能引用事件与时间线就不重复描述整段屏幕

## 6. 第一阶段产品形态

第一阶段产品形态应定义为：

> 一个本地运行的进程级视觉监控与时间线问答工具。

它应具备两种主要工作模式：

### 6.1 长时监控模式

用户选择一个目标进程后，Ayes 长时间运行并持续监控该进程相关窗口，识别有价值变化并存入时间线。

### 6.2 即时回放问答模式

用户在任意时刻可以针对最近 5-15 分钟的视觉时间线进行提问，例如：

- 刚才发生了什么？
- 最近 10 分钟这个进程有哪些异常？
- 为什么现在出现这个界面？
- 登录状态是什么时候失效的？
- 有没有出现验证码、断连、报错或者超时？

## 7. 第一阶段推荐技术路线

第一阶段固定采用以下路线：

> OCR + 向量语义匹配 + 轻量视觉标签

明确不采用以下路线作为 MVP 主线：

- 不以 YOLO 为第一优先
- 不一开始训练复杂视觉检测模型
- 不先追求通用多模态理解

### 7.1 为什么不先走 YOLO 主线

YOLO 的价值主要体现在固定 UI 场景下的目标定位和类别识别，但当前第一阶段核心问题是：

- 过去几分钟发生了什么
- 哪些变化与用户关注目标相关
- 是否需要推送告警
- 如何支持提问回放

这些问题的主信号在第一阶段仍然是：

- OCR 文本变化
- 窗口标题变化
- 区域内容变化
- 轻量事件标签
- 时间顺序

因此，YOLO 属于第二阶段增强项，而不是 MVP 的基础依赖。

## 8. 第一阶段系统架构

第一阶段建议拆成以下模块：

### 8.1 目标进程与窗口发现层

负责：

- 识别指定进程
- 枚举进程关联窗口
- 跟踪窗口新增、关闭、隐藏、最小化、层级变化
- 维护窗口身份和生命周期

这是第一阶段最关键的入口层。

### 8.2 采集层

负责：

- 对目标窗口进行周期性采样
- 尽可能覆盖前台、后台、遮挡、折叠、最小化等状态
- 记录采样结果是否成功、失败或不可见
- 对不可直接采集的窗口保留状态事件

注意：

“最小化窗口也要检测得到”是产品目标，但在不同系统和技术路径下不一定都能拿到实时像素内容。因此第一阶段必须明确区分：

- **窗口状态可观测**
- **窗口像素可采集**

如果最小化窗口无法直接获取实时像素，系统至少要：

- 感知其状态变化
- 记录相关时间点
- 在恢复可采集时快速补齐变化分析

### 8.3 变化检测层

负责：

- 帧差分
- ROI 检测
- 文本块变化检测
- 大区域变化检测
- 静态区域跳过
- 相同内容去重

该层决定系统是否进入重处理流程。

### 8.4 OCR 与文本结构化层

负责：

- 对变化区域做 OCR
- 提取标题、正文、按钮文案、表格片段、数值、日志片段
- 对 OCR 结果做清洗、分块、归一化
- 保留区域坐标和窗口上下文

### 8.5 轻量视觉标签层

第一阶段不做复杂检测模型，而是做轻量标签归类，例如：

- `dialog`
- `error_like`
- `status_change`
- `form_change`
- `table_delta`
- `notification_like`
- `captcha_like`

这些标签可以来自：

- 规则
- OCR 关键词
- 窗口结构信号
- 区域变化形态

### 8.6 语义匹配层

负责：

- 将用户自然语言监控目标转为可执行监控配置
- 对事件文本、标题、摘要、标签做 embedding
- 对监控意图做 embedding
- 判断某次事件是否与“重点关注内容”相关

第一阶段语义匹配只服务两个目的：

- 判断是否应该重点记录或推送
- 支持用户基于语义查询最近时间线

### 8.7 事件抽取层

负责将多种原始信号压缩成结构化事件，事件至少包含：

- 时间
- 进程
- 窗口身份
- 事件类型
- 变化区域
- OCR 文本
- 事件摘要
- 标签
- 优先级
- 置信度
- 是否命中监控意图

### 8.8 短时时间线存储层

负责：

- 保存最近 5-15 分钟事件
- 保存事件引用关系
- 保存必要截图切片或定位引用
- 支持按时间、窗口、标签、语义进行检索

第一阶段只保留短时时间线，不做无限长历史归档作为核心目标。

### 8.9 告警推送层

负责：

- 命中重点事件时触发告警
- 企业微信 webhook 推送
- 去重
- 冷却时间控制
- 优先级阈值控制

### 8.10 提问回放层

负责：

- 回答最近几分钟发生了什么
- 回答某窗口或某进程为什么变成当前状态
- 从时间线中提取关联事件
- 返回结构化摘要，而不是盲目重新读整段屏幕

## 9. 用户自然语言监控目标

第一阶段允许用户使用自然语言描述要重点关注的变化，例如：

- 关注报错、断连、验证码、登录失效
- 关注状态栏颜色变化和告警弹窗
- 关注页面卡死、超时和失败提示
- 关注数字异常波动或者表格中关键字段变化

但 Ayes 不应直接把这类自然语言当作底层执行逻辑，而应经过一个中间层转换为 `watch spec`。

建议工作方式：

1. 用户输入自然语言监控目标
2. 上层 Agent 或编译器将其转成结构化 `watch spec`
3. Ayes 负责执行 `watch spec`

这能保证边界清晰：

- Ayes 负责执行与检索
- 上层负责自然语言理解和配置生成

## 10. Watch Spec 设计

第一阶段应围绕 `watch spec` 建模。

建议结构示例：

```json
{
  "target": {
    "type": "process",
    "process_name": "TargetApp",
    "include_all_windows": true
  },
  "sampling": {
    "interval_ms": 1500,
    "retain_minutes": 15
  },
  "watch_intent": {
    "summary": "关注报错、验证码、断连、登录失效、长时间无响应",
    "semantic_queries": [
      "error message",
      "captcha shown",
      "session expired",
      "disconnected",
      "timeout"
    ],
    "rules": [
      {
        "type": "text_contains",
        "any": ["错误", "失败", "超时", "验证码", "重新登录", "断开连接"]
      },
      {
        "type": "window_title_change"
      },
      {
        "type": "large_region_change"
      }
    ]
  },
  "alert": {
    "enabled": true,
    "channel": "wecom_webhook",
    "priority_threshold": "medium",
    "cooldown_sec": 120
  }
}
```

## 11. 事件模型

第一阶段统一输出结构化 JSON 事件。

建议最小结构：

```json
{
  "event_id": "evt_xxx",
  "timestamp": 0,
  "process_name": "TargetApp",
  "window_id": "win_xxx",
  "window_title": "",
  "window_state": "visible|hidden|minimized|occluded|closed|unknown",
  "event_type": "text_change|status_change|dialog|error_like|notification_like|window_lifecycle",
  "priority": "low|medium|high",
  "confidence": 0.0,
  "matched_watch_intent": true,
  "region": {
    "x": 0,
    "y": 0,
    "w": 0,
    "h": 0
  },
  "ocr_text": "",
  "summary": "",
  "tags": ["ocr", "semantic_match"],
  "evidence_refs": ["snap_xxx", "roi_xxx"]
}
```

## 12. 时间线问答能力

第一阶段必须支持基于最近 5-15 分钟时间线的问答。

最核心的问题包括：

- 最近 5 分钟发生了什么？
- 最近 10 分钟有哪些异常？
- 某个窗口是什么时候发生关键变化的？
- 为什么当前界面会变成这样？
- 哪次变化最值得关注？

问答流程建议为：

1. 接收问题
2. 将问题转成事件检索条件
3. 从短时时间线中取回候选事件
4. 补充必要上下文
5. 生成结构化回答

第一阶段要严格避免：

- 每次问答都重新全量 OCR
- 每次问答都重新扫描所有截图
- 让问答路径完全依赖大模型自由发挥

## 13. 企业微信告警

企业微信 webhook 是第一阶段的标准告警出口。

告警触发条件建议包括：

- 命中监控意图
- 事件优先级达到阈值
- 未命中去重或冷却限制

告警内容应包含：

- 时间
- 进程名
- 窗口标题
- 事件摘要
- 关键 OCR 文本
- 事件优先级
- 可选事件引用 ID

## 14. MVP 定义

第一阶段 MVP 必须严格控制范围，只做以下内容：

### 14.1 必做

- 指定进程监控
- 自动发现该进程下的窗口
- 长时运行
- 定时采样
- 差分检测
- OCR 文本抽取
- 轻量视觉标签
- 事件结构化
- 最近 5-15 分钟时间线存储
- 基于语义匹配的重点事件识别
- 企业微信 webhook 告警
- 基于时间线的提问回放

### 14.2 不做

- YOLO 训练与复杂检测模型
- 全桌面无差别监控
- 全自动鼠标键盘操作
- 复杂多 Agent 编排
- 长期历史无限存储
- 过度通用的视觉理解
- 复杂工作流编排系统

## 15. 关于最小化/折叠窗口的现实约束

“指定进程下所有窗口，哪怕折叠或最小化也要尽量检测”属于核心产品要求，但必须正视技术现实：

- 某些窗口状态下可以拿到元数据，但拿不到实时像素
- 某些窗口状态下只能通过系统 API 或窗口缓冲区间接采样
- 某些应用本身渲染策略会让后台/最小化窗口内容不可直接观测

因此第一阶段开发原则是：

1. 把“窗口状态感知”和“窗口像素采集”拆开建模
2. 把“可观测性”作为一等公民写入事件系统
3. 对无法实时取像素的窗口，至少记录生命周期和状态变化
4. 在恢复可见或可采集时进行补充分析

这部分是实现难点，不允许在产品设计上假装不存在。

## 16. 后续阶段的 YOLO 位置

YOLO 是第二阶段增强项，不是第一阶段基础能力。

适合第二阶段加入 YOLO 的情况：

- 已经明确一个高价值垂直场景
- 已经积累了真实截图和标注
- OCR 和规则无法稳定识别关键非文本目标
- 需要识别固定类型 UI 组件

第二阶段优先识别对象可包括：

- 弹窗
- 错误框
- 通知条
- 状态灯
- 红点提醒
- 二维码
- 固定业务面板块

## 17. Skill / Tool / Agent 接入策略

第一阶段结论明确：

> 先做本地工具/服务，再封装成 skill。

原因：

- skill 只是入口形态，不是核心能力
- 当前最难的是采集、时间线、事件提取、检索和问答
- 先把核心引擎打稳，后续才能稳定接入 OpenClaw、Codex、MCP 和其他 Agent

但第一阶段从一开始就应按未来 skill 化设计接口。

建议预留接口：

- `watch.create`
- `watch.start`
- `watch.stop`
- `watch.status`
- `timeline.query`
- `timeline.recent`
- `timeline.explain`
- `alerts.test`
- `snapshot.inspect`

## 18. 商业化切入点

第一阶段更容易落地的切入口包括：

- 客服后台监控
- 云手机/虚拟屏幕任务监控
- 运维控制台异常监控
- 长时间无人值守任务监控
- 交易和高频工作台异常提示

商业化卖点不应表述为“更强 OCR”，而应表述为：

- 给 AI 和人类提供可提问的视觉时间线
- 给长期任务提供重点变化监控和告警
- 给指定进程提供短时视觉记忆与回放能力

## 19. 第一阶段结论

Ayes 第一阶段的正确定位是：

> 一个面向指定进程全窗口监控的视觉时序回放工具，基于 OCR、语义匹配和轻量视觉标签，将最近几分钟的界面变化压缩成可检索、可提问、可告警的结构化事件流。

第一阶段的正确路线是：

- 先做人类用户提问回放
- 先做本地工具/服务
- 先做指定进程全窗口监控
- 先做 OCR + 语义匹配 + 轻量视觉标签
- 先做 5-15 分钟短时视觉时间线
- 先打通企业微信 webhook 告警

第二阶段再考虑：

- YOLO
- skill 化
- MCP 化
- 面向更多 Agent 的接入
