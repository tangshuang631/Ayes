# 21 对话式任务规划与配置确认流

## 1. 文档目标

本文件定义 Ayes 从自然语言到 `watch spec` 的正式编排层。

目标不是替代 `watch spec`，而是补出以下缺口：

- 智能体如何把用户自然语言请求转成任务草案
- 哪些字段可以自动推断，哪些字段必须确认
- 智能体下一轮应该补问什么
- 草案如何进入最终可执行 `watch spec`
- Web 工作台和 skill 如何共享同一条配置确认流

## 2. 设计原则

- 正式执行配置仍然以 `watch spec` 为准
- 对话式规划器只负责生成草案，不直接偷偷启动监控
- 草案必须显式暴露缺失项、歧义项和默认值
- skill / CLI / HTTP API / Web 工作台必须共用同一份草案结构
- 无法可靠推断的 ROI、点击点、webhook URL 不得伪造
- 对话式补问必须依赖正式结构字段，不能只靠 skill 文案临场猜测

## 3. 规划器在系统中的位置

第一阶段新增正式编排层：

1. 用户或智能体给出自然语言任务
2. `planner` 读取自然语言、可选目标提示、可选候选目标摘要
3. 输出 `watch plan draft`
4. 若存在缺失项或歧义项，进入配置确认流
5. 用户或智能体确认后，草案转成最终 `watch spec`
6. 再由监控服务装载并启动

明确约束：

- `planner` 不直接访问底层采集实现
- `planner` 只产出结构化草案和确认说明
- 执行层仍通过 `/api/watch/load-configured` 或等价正式执行入口装载最终 spec

## 4. Watch Plan Draft 结构

规划层输出必须采用稳定结构：

```json
{
  "plan_version": "1.0",
  "task_id": "task_xxx",
  "user_prompt": "帮我监控某商品价格低于 299 时提醒我",
  "draft_spec": {},
  "mode": "triggered",
  "intent_category": "price_watch",
  "target_hint": {
    "type": "process",
    "process_name": "Google Chrome"
  },
  "resolved_target": {
    "type": "process",
    "process_name": "Google Chrome"
  },
  "missing_fields": [
    {
      "field": "alert.webhook_url",
      "reason": "triggered 模式需要可用通知出口"
    }
  ],
  "questions": [
    {
      "question_id": "q_regions_scope",
      "kind": "region_scope",
      "field": "target.regions",
      "prompt": "这次要监控整个目标，还是只监控几个重点区域？",
      "required": true,
      "suggested_answer": "先只监控价格区和库存区"
    }
  ],
  "region_intents": [
    {
      "region_intent_id": "ri_price",
      "name": "价格区",
      "purpose": "读取当前价格并判断阈值",
      "required": true,
      "status": "needs_binding"
    }
  ],
  "action_intents": [
    {
      "action_type": "refresh_click",
      "purpose": "周期性刷新页面以便发现状态变化",
      "required_confirmation": true,
      "missing_fields": ["actions.refresh_click.point"]
    }
  ],
  "ambiguities": [],
  "assumptions": [
    "未显式指定短期记忆时默认保留 15 分钟",
    "未显式指定长期记忆时默认保留 24 小时"
  ],
  "confirmation_summary": [
    "将监控 Google Chrome 代表业务窗口",
    "命中价格低于 299 时发送 webhook 告警"
  ],
  "can_apply_directly": false
}
```

要求：

- `draft_spec` 必须已尽量接近最终 `watch spec`
- `missing_fields` 必须列出阻止直接执行的关键缺口
- `questions` 必须给出下一轮智能体应补问什么
- `region_intents` 必须给出待绑定区域的名称和用途
- `action_intents` 必须给出待确认动作及其缺口
- `ambiguities` 必须列出多解场景，例如多个候选目标都可能匹配
- `assumptions` 必须列出规划器自动采用的默认值
- `confirmation_summary` 必须可直接给用户或智能体复述

## 5. 自动推断边界

以下字段允许自动推断：

- `mode`
- `watch_intent.summary`
- `watch_intent.queries`
- 常见数值阈值规则
- 常见记忆默认值
- 常见采样默认值
- 是否建议开启视觉增强

以下字段必须谨慎推断：

- `target.process_name`
- `target.window_id`
- `target.screen_id`
- `target.regions`
- `actions.refresh_click.point`
- `alert.webhook_url`

以下字段默认不自动生成，除非用户明确指定或已有外部选择结果：

- ROI 详细坐标
- 刷新点击坐标
- 企业微信 webhook 实际地址

以下字段允许先生成“意图层”而不是最终值：

- `target.regions`
- `actions.refresh_click`

也就是：

- 区域可以先生成 `region_intents`
- 点击动作可以先生成 `action_intents`
- 等用户或智能体补问确认后，再转入最终 spec

## 6. 配置确认流

配置确认流必须支持两种状态：

- `ready`
- `needs_confirmation`

判定规则：

- 缺失关键字段时必须为 `needs_confirmation`
- 存在目标歧义时必须为 `needs_confirmation`
- 仅使用安全默认值且已具备执行条件时可为 `ready`

确认阶段至少要能回答：

- 监控哪个目标
- 监控哪些 ROI
- 这些 ROI 分别是做什么用的
- 命中什么条件
- 是否需要 webhook
- 是否需要刷新点击
- 刷新点击的频率和坐标空间
- 记忆保留多久

### 6.1 questions 合同

`questions[]` 是本阶段 skill-first 路线最关键的补问合同。

每个问题至少应有：

- `question_id`
- `kind`
- `field`
- `prompt`
- `required`
- `suggested_answer`

第一阶段至少支持：

- `target_missing`
- `region_scope`
- `region_definition`
- `region_binding`
- `webhook_missing`
- `refresh_click_enable`
- `refresh_click_point`
- `refresh_click_interval`

## 6.2 region_intents 合同

`region_intents[]` 用于先表达“这个任务希望监控哪些重点区域”，即使真实坐标暂时还没有。

每个区域意图至少应有：

- `region_intent_id`
- `name`
- `purpose`
- `required`
- `status`

当前状态至少支持：

- `needs_binding`
- `bound`
- `skipped`

### 6.2.1 region_bindings 合同

`region_bindings[]` 是从区域意图进入最终 ROI 坐标的正式桥梁。

它服务于 skill / agent 与外部选择器、截图标注器之间的协作，而不是服务于 Web 页面。

每个绑定项至少应有：

- `region_intent_id`
- `region_id`
- `name`
- `x`
- `y`
- `w`
- `h`
- `coordinate_space`
- `source`

其中 `source` 当前至少支持：

- `external_selector`
- `screenshot_annotation`
- `manual_coordinates`

正式约束：

- 智能体不必自己口头推断像素坐标
- 智能体可以引用外部选择器或截图标注器返回的 `region_bindings[]`
- `confirm-plan` 必须能够把 `region_bindings[]` 转成最终 `target.regions`

## 6.3 action_intents 合同

`action_intents[]` 用于表达待确认动作，当前重点是：

- `refresh_click`

每个动作意图至少应有：

- `action_type`
- `purpose`
- `required_confirmation`
- `missing_fields`

第一阶段不要求动作意图一定已具备可执行坐标，但必须让智能体知道下一句该补什么。

## 7. API 与工具入口

第一阶段正式新增以下能力面：

- `POST /api/agent/plan-watch-spec`
- `POST /api/watch/confirm-plan`

对应本地工具能力面：

- `ayes-agent plan-spec`
- `ayes-agent confirm-plan`

要求：

- `plan-spec` 只返回草案与确认说明
- `plan-spec` 还必须返回 `questions[]`
- `confirm-plan` 负责把确认后的草案转成最终装载结果
- `confirm-plan` 应优先接受 `region_bindings[]` 这类外部绑定结果
- skill 优先通过这两个入口完成自然语言任务编排，而不是手写 spec

## 8. Skill 与 Web 的协作边界

skill / CLI 适合：

- 根据自然语言生成任务草案
- 让智能体逐条读取 `questions[]` 并补问
- 接收外部选择器或截图标注器返回的 `region_bindings[]`
- 在用户已指定目标后完成装载
- 回读状态、事件、记忆、截图和告警

Web 工作台适合：

- 目标候选预览
- ROI 框选
- 点击点选取
- 人类核验截图和当前实际采集目标

如果用户只通过智能体对话配置任务，必须允许以下能力：

- 指定整个屏幕
- 指定某个进程
- 指定简单 watch intent
- 指定时间范围和记忆策略
- 指定是否开启 webhook / 视觉增强

涉及 ROI 和点击点时，默认应允许智能体回退为：

- 先通过 `region_intents` 或 `action_intents` 明确意图
- 若仍缺真实坐标，再让外部选择器或截图标注器返回 `region_bindings[]`
- 然后由智能体继续 `confirm-plan`

## 9. 第一阶段实现结论

当前阶段正式结论如下：

- 自然语言到 `watch spec` 的编排层必须成为正式模块
- 规划器必须输出草案、缺失项、歧义项和确认摘要
- 规划器必须稳定输出 `questions[] / region_intents[] / action_intents[]`
- 区域绑定必须优先通过 `region_bindings[]` 进入 `confirm-plan`
- `watch spec` 仍是唯一执行契约
- Web 与 skill 必须复用同一配置确认流
